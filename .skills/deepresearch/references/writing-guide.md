# 写作指南

## 报告格式

报告语言在首次成文时锁定：用户明确指定时遵从用户；否则与用户原始问题及已确认大纲的主语言一致。标题、摘要、目录、章节名、表格、图注、参考文献标题和页脚统一使用该语言，不因引用来源或局部术语切换整篇语言。

| 结构角色 | 中文报告 | English report |
|---|---|---|
| 摘要 | 摘要 | Abstract |
| 目录 | 目录 | Table of Contents |
| 结论 | 结论 | Conclusion |
| 参考文献 | 参考文献 | References |

下列花括号内容是结构占位符，成文时必须替换为报告语言对应文字，不得原样保留：

```markdown
# [研究标题]

**{摘要标题}**

[用报告语言写 2–4 句话概括核心发现；直接说结论，不用空泛的“本文将……”式开场]

## {目录标题}

## [章节标题]

### [子节标题]
[内容，织入引用脚注如 [^1][^2]]

...

## {结论标题}
[直接回答核心研究问题。若用户要求评估、推荐或预测，必须给出明确判断，不能只罗列信息而不表态]

## {参考文献标题}
[^1]: 标题 — URL
[^2]: 标题 — URL
...
```

主章节不少于 3 个时保留对应语言的目录标题，但不要手写或 patch 目录项，只修改正文标题。`save_report.py` 会自动生成并在每次修改后刷新目录；总条目不超过 20 时列出主章节和子节，超过时只列主章节。

## 起草时的写作要求

**内容层面**

- **来源铁律**：所有数据、案例、结论必须来自阶段 4 已保存的任务结论或阶段 5 反思修正，禁止凭空生成
- **反幻觉规则**：涉及具体数字（市场规模、排名、时间节点、人物言论）时，必须能在结论或反思引用的来源中找到对应原文。结论未包含某数据点时，宁可用报告语言明确说明公开数据有限，也不要编造。**尤其禁止虚构未来事件的具体数据**（未上映电影票房、未发布产品销量等）
- **跨来源综合**：优秀的见解来自多个来源的交叉验证和模式识别，不是逐条摘录。有多来源信号时用报告语言的综合表达；只有单来源支持时如实呈现，不虚构合并
- **定量问题给数字**：用户问题含“比重是多少”“数量、比例”等明确数量要求时，结论有数据 → 给具体值或估计区间并说明推算依据；结论无数据 → 用报告语言说明公开数据有限，不推算、不编造估算区间
- **维度语义忠实**：用户命名的每个维度按字面语义理解，不得偷换。"融资情况"指实际融资活动（债券发行、配股、信贷额度），≠ "资本充足率/偿付能力"；"增长幅度"指业绩增速，≠ "市场地位"。遇到模糊维度，在章节首句说明理解方式，不得悄悄替换
- **预测要有数量级与时间节点**：趋势预测不能只用"将增长"、"会扩大"等定性词汇。有支撑数据时给出具体时间节点（"到 2027 年"）和数量级（"预计年均增长 X%"）；数据不足时说明制约预测的核心不确定因素，不虚构数字
- **数据时效性**：引用超过 2 年的核心数据需标注获取年份；超过 3 年的需说明是否存在更新来源
- **批判性分析**：对报告中的主要论点或建议，不能只说"有效"或"推荐"，还要说明：在什么条件下适用、已知局限、是否有不同声音（限于结论已包含的信息）
- **机制分析**（技术/科学课题）：对每个关键结论说清"为什么"——驱动该现象的机制。比较方案时，解释选择某方案的本质原因和局限来自哪个底层约束
- **结论有态度**：遇到"哪家公司最值得关注""哪个方向最有前景""这个思路是否可行"等问题，结论部分给出明确判断，不用"各有优劣，需具体情况具体分析"敷衍
- **大纲结构不漂移**：保留用户确认大纲的覆盖范围与章节顺序。章节标题可以润色、缩短或改成更适合正文的表达，但不得改变章节含义、删除用户明确要求的维度，或用无关标题替代原章节

**多实体比较的一致性模板**

当需要比较 N 个公司、研究组、国家、方案等实体时：
- **统一子标题结构**：每个实体的介绍段落使用完全相同的子标题顺序
- **用户指定的比较维度 = 子标题**：直接用作每个实体的子标题（或汇总表格列名），保持原措辞
- **汇总表格**：N ≥ 3 个实体时，优先在章节末尾加一张汇总对比表；缺信息的格用报告语言注明公开信息有限，而非留空

**表达层面**

- **受众适配**：始终对齐阶段 1 判断的受众类型
  - 所有缩写首次出现必须写全称，并用报告语言解释；中文报告可写“TEACCH（结构化教学系统）”，英文报告不得为缩写补中文释义
  - 面向普通读者：每个抽象概念配具体例子，每个建议说明如何落地，避免连续堆叠专业术语
  - 面向专业读者：精准术语为主，数据和具体方案比理论描述更重要
  - **受众不确定时默认为"普通读者"模式**
- **多项对比用表格**：多个方案/公司/国家/方法的横向比较优先用对比表格
- **合成型报告**：课题要求"总结/梳理/分析趋势"时，提炼模式而非完整列举。每个趋势选 2–3 个最典型案例
- **筛选型报告**：入选项占主篇幅，排除项用一段话统一说明排除原因
- **人群画像报告**：数据外每个细分人群需要有叙事段落
- **技术类报告**：密集使用专业缩写（≥5 个）时，目录后加缩写说明表
- **不重复**：后续章节不复述前章已有内容；同一 URL 只出现一次
- **段落长度控制**：单段 ≤200 字；一段只讲一个话题；列表项超过 5 条时改用表格
- **摘要写法**：首句直接给出最重要结论，不用“本报告将探讨…”或“This report will explore…”开头；结论含具体数字时给出数字（含区间和置信度），否则用定性表述；2–4 句覆盖核心结论 + 最意外发现 + 关键启示

**引用格式**

- 正文中用 `[^1]`、`[^2]` 标注，文末统一列出；编号由 `save_report.py` 自动按 References 列表定义顺序重编，无需手动排序
- 只记录任务结论或反思修正中出现的来源
- 来源标题与 URL 从任务结论或反思中原样复制，不改写标题，不手工截断、拼接或补全 URL，也不得替换为机构首页、DOI 入口或其他看似等价的地址
- 参考文献每个来源只出现一次；URL 必须完整可访问
- 含 `{占位符}` 的协议或地址示例用行内代码表示，它不是来源，不得列入参考文献；参考文献中的 URL 不得含占位符
- 首次调用 `save_report.py --write` 后，任务结论与反思材料视为冻结；报告阶段发现引用或表述问题时修改正式报告，不得通过补写、替换任务结论或反思中的标题、URL 来绕过引用校验

**报告阶段允许的写作技巧**（与 SKILL.md 6.4「报告内容边界」配套）

以下动作允许：
- 添加过渡句、章节引言、段落衔接
- 合并多个任务的共同发现
- 基于已有结论，用报告语言做谨慎推论，推论强度不超过依据强度
- 对已有结论进行去重、重组、按大纲重新排布

反思结论中的「报告写作提醒」控制**措辞、限制、比较范围**，不新增事实内容——把它当作正文表述的边界，而不是新素材。

**图表写作规范**（与 SKILL.md 6.3 配套）

- 图表标题写**结论**而非数据名（例："在同一版本 HLE 下 A 领先 B、C" 而非 "HLE 得分对比"）
- 每张图正文中至少一段文字解释该图揭示的结论
- 图安排在**首次讨论对应数据的章节**中，不能全部堆到附录
- 图表来源必须与正文引用共用参考文献编号，不允许模糊标注
- 图表标题、坐标轴、图例、数据标签、图注和图片说明必须与报告语言一致；专有名词和原文名称除外
- 最终图片须先保存到 `<PROJECT_ROOT>` 内；Markdown 图片语法独占一行。位于 `outputs/` 的图片从 `reports/report.md` 引用时使用 `../outputs/chart_N.png`

**篇幅**：用户未明确指定最低字数时，`save_report.py` 对字数不做任何限制，也不输出字数信息；完成结构与核心回答后立即调用 `--write`，不为篇幅计字或扩写，首稿前不另建临时草稿。结论素材不足时不为凑字数扩写背景或重复内容。用户明确指定最低字数时加 `--min-words N`。

## 起草后：修订检查

起草完成后，做一轮快速扫描，重点检查以下问题：

| 检查项 | 常见问题 |
|--------|---------|
| 报告类型与格式是否对应？ | 合成型是否在"提炼趋势"而不在"枚举清单"；筛选型是否把篇幅重心放在入选项；人群画像是否有叙事层 |
| 用户每个问号有没有直接回答？ | 扫描用户原始提问中的每个"？"——报告中是否有段落明确回答 |
| 定量问题有没有给数字？ | 结论提供数据时，报告是否给了具体值或区间；结论无数据时是否用报告语言说明公开数据有限而非编造 |
| 并列子问题深度是否均衡？ | 用户并列提出 N 个问题时，各问题覆盖比例是否 ≤ 2:1 |
| 比较分析实体维度是否完整？ | 对比表格中缺信息的格是否用报告语言注明公开信息有限而非留空 |
| 预测有数量级和时间节点？ | 有数据时给出具体年份和数量级；否则说明不确定因素，不虚构数字 |
| 数据时效性是否注明？ | 超过 2 年的核心数据是否标注了获取时间 |
| 子问题清单全部覆盖？ | 用户明确提出的每个维度/子问题都有对应章节 |
| 用户指定维度是否成了章节标题？ | 不合并、不替换用户命名的维度，不新增用户未要求的同级维度 |
| 多实体比较是否以实体为主轴？ | 当用户要求"N 个公司/方案各自提供 X/Y/Z"时，每个实体独立成节 |
| 研究主体/范围有没有越界？ | 若用户限定了地域、学科、时间范围，检查是否有章节超出 |
| 用户提及的框架原理有没有介绍？ | "GCS算法"、"PRM"等具体技术需有基础原理说明 |
| 结论有没有明确表态？ | 用户问"哪个最好/是否可行"，结论必须判断 |
| 批判性视角有没有缺席？ | 结论包含局限时，报告是否复述了这些局限 |
| 机制/原因有没有解释清楚？ | 每个关键结论后面是否回答了"为什么" |
| 摘要数字与正文是否一致？ | 摘要给出估算数字时，正文推算步骤必须能得出同一区间 |
| 用户指定维度是否按字面理解？ | "融资情况"≠"资本充足率"；"增长幅度"≠"市场地位" |
| 多实体比较结构是否统一？ | 每个实体的子标题顺序是否完全一致 |
| 摘要是否符合规范？ | 首句是否直接给出最重要结论？是否避免“本文将……”或“This report will…”开头？ |
| 受众适配：缩写是否解释？ | 面向普通读者时，不只是写全称，还要有一句话解释含义 |
| 受众适配：有没有可操作实例？ | 面向实践者时，每个建议是否有"怎么做"步骤 |
| 有没有虚构/无来源的数据？ | 所有具体数字是否都能在任务结论或反思修正中找到对应引用；尤其警惕虚构未来事件数据 |
| 段落长度是否超标？ | 是否有单段 >200 字的情况 |
| 对比内容有没有用表格？ | 多项并列内容如用文字段落描述，改为表格 |

## 保存报告

完成结构与核心回答后，直接将完整 Markdown 作为 stdin 调用 `<SKILL_ROOT>/scripts/save_report.py --write`；用户明确指定最低字数时加 `--min-words N`，否则首稿前不自行计字数。脚本写入正式的 `<PROJECT_ROOT>/reports/report.md`，锁定并校验中英文报告语言，自动维护对应语言的目录，校验通过后生成 `<PROJECT_ROOT>/reports/report.docx`。

`--write` 用于首次完整成文。仅当语义检查发现整体方向、结构或多数章节需要推翻时，可再使用一次 `--write` 全文替换；全文发生变化的 `--write` 总计最多 2 次。局部增补、纠错和章节替换均使用 `--patch`；只合并相互独立且取自当前 `report.md` 的替换，`PATCH_REJECTED` 后重新读取报告，不复用旧补丁。不得另建草稿、直接编辑 `report.md`、直接调用 `report_renderer.js` 或加载 docx skill。

脚本返回 `RENDERED: yes` 只表示机械校验与 DOCX 渲染成功，不表示报告语义已经通过。`REVIEW_SCOPE: full` 时完整完成一轮上方检查并先汇总问题，再尽量用一次 `--patch` 处理；补丁成功后若返回 `REVIEW_SCOPE: targeted`，只复核修改处及受影响内容，不重新开始全文检查。全部必检项为 `PASS` 后，调用 `save_report.py --finalize` 提交审查结果，待返回 `WORKFLOW_STATE: REPORT_READY_TO_DELIVER` 后方可进入交付。
