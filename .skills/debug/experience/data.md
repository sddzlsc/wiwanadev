# 数据层 Debug 准则

适用症状：列表为空、下拉框无选项、查不到记录、数据不显示、计算结果错误、删除报外键错误。

---

## 数据缺失/查不到

### 先查库确认真实数据状态

遇到"下拉框为空/查不到记录/某类数据不显示"时，第一步直连数据库查：

- 目标表有多少条记录
- 关键外键/属主字段是否为空
- 记录与当前用户的真实关联方式

只有确认数据确实存在后，才去看查询逻辑和前端渲染。很多"前端不显示"的根因是数据层本身为空或关联字段为 NULL。

### 修改 DB 函数前先核对真实 schema

改 PostgreSQL 函数 / Edge Function / RPC 前，先查 information_schema 确认列名、表名、关联字段的真实情况。遇到 "column/table does not exist" 报错时，先回查 schema 确认是字段被重命名、表被合并还是根本不存在，而不是逐个按报错信息补丁。

### PostgREST/Supabase 查询关联

- to-one FK 关系：嵌套查询返回单个对象
- to-many FK 关系：嵌套查询返回数组
- 确认 JOIN 条件是否正确关联到目标记录
- 确认查询有没有额外的 WHERE 过滤把目标记录排除

---

## 数据一致性

### 初始化/兜底 upsert 不要覆盖用户状态

对"仅用于保证记录存在"的初始化操作，使用 ignoreDuplicates / ON CONFLICT DO NOTHING。需要更新时再显式调用 update/upsert。进度、配置、计数器等状态写入必须先看是否允许覆盖。

典型场景：页面 onFocus 无条件 upsert 重置了用户已有的进度/状态。

### 删除级联依赖实体前清理外键引用

删除用户/记录前：

- 扫描所有指向被删表的外键列
- 按 NULLABLE/NOT NULL 分别置空或转移到保留账号
- 修改 API 返回字段后同步校验前端消费代码中的字段名

---

## 业务计算逻辑

### 规则型计算按业务对象类型分支

涉及规则型计算（涨跌幅、税率、费率、权限、状态机、校验规则等）时，先识别业务对象的分类属性（板块/角色/类型），再用查表或配置化分支逻辑。禁止把最常见的一类规则写死成全局默认值。

### 数据识别/筛选前确认用户真实取值

遇到"某类数据没被识别/没参与计算/数量为0"时：

- 先定位负责筛选/识别的函数
- 检查匹配规则是否覆盖用户的真实数据写法
- 从精确匹配固定名单扩展为包含关键字/模糊匹配，留兜底分支
- 用用户提供的原始数据验证规则是否命中

---

## 排查顺序（定位根因用）

1. 直查数据库：目标表是否有数据、数量是否符合预期
2. 查关联字段：外键/属主字段是否为 NULL 或指向错误记录
3. 查查询逻辑：WHERE/JOIN 条件是否把目标记录过滤掉
4. 查 RLS 策略：当前用户角色是否有权读取（见 [auth.md](auth.md)）
5. 最后才查前端渲染逻辑
