# 国内秒哒应用规格
页面：首次设置、今日、7日餐历、购物清单、备餐计划、周复盘、设置与删除。
状态：idle → validating → generating → ready 或 failed。局部重试保留档案和锁定餐次。
默认使用带 `VITE_APP_ID` 前缀的 `localStorage`，无需注册即可保存档案、周计划、餐次、饮食记录和复盘；刷新与重新打开后恢复。只有用户明确要求账户、跨设备历史或协作时才启用 Supabase，再建 profiles、weekly_plans、meals、food_logs、reviews，并全部启用 user_id RLS。
验收：
1. 花生过敏时主餐与所有替换项均无花生。
2. 替换一道晚餐后营养汇总和购物数量同步更新。
3. 保存计划刷新后仍存在。
4. 模型失败时保留全部输入并可重试。
5. 生产构建从 `/` 进入后可正常导航，刷新食谱、档案、购物、备餐、记录和复盘页面均不出现 404 或空白页。
6. 未启用 Supabase 匿名登录时，免登录版本仍可完成建档、保存和刷新恢复；账户版则显示可用登录入口和明确错误态。


## 模型能力绑定与运行实现（强制）
1. 本节只适用于明确的应用生成任务。普通营养分析、食谱、复盘和调整计划请求直接由业务 Skill 回答，不调用额外模型 Skill。确认用户要生成应用后，自动调用 `@文本生成大模型`，不要求用户再次点名模型。
2. 生成轨迹必须能确认模型 Skill 被真实加载；正文中出现普通 `@文字`、展示一个模型名称或写一段假调用均不算绑定。
3. 食谱生成、单餐替换与周复盘使用该模型 Skill 提供的官方实现。不得自行请求 `qianfan.baidubce.com` 或其他模型 Endpoint，不得自行拼接 `Authorization: Bearer ${INTEGRATIONS_API_KEY}`。
4. 单餐替换只向模型提交目标日期、餐次、已锁定餐次、剩余营养预算和完整硬约束；响应只能更新该餐次，再由确定性代码重算日/周汇总及购物清单。不得请求整周后循环覆盖一个餐位。
5. 请求失败时使用本次创建记录的真实 ID 写入 `failed`，并保留档案、输入和锁定餐次；React 异步流程不得依赖尚未更新的闭包状态。
6. 过敏原命中任一主食材、调料、酱料、加工成分或替换项时，整道候选餐必须淘汰并重新生成，不能通过删除命中食材来保留原菜。
7. 营养值来自确定性数据表或明确标注的估算数据；模型输出不得冒充权威食品数据库。

### 流式模型调用与解析（强制）
1. SSE 消费函数必须返回一个在 `[DONE]`、`reader.done` 或明确失败后才 settle 的 Promise。使用 `ReadableStreamDefaultReader` 时采用可等待的 `while (true) { await reader.read() }` 循环，或把读取完成封装为 Promise 并由外层 `await`；禁止调用递归 `read()` 后立即从请求函数返回。
2. 在流完成前不得执行 JSON 提取、候选过滤、空结果判断或关闭 loading。必须先拼接完整模型文本，再去除可选代码围栏，解析 JSON，校验候选数组结构，最后执行过敏原硬过滤。
3. 明确区分四种结果：HTTP/网关失败、SSE 读取失败、JSON/Schema 解析失败、解析成功但经业务约束过滤后确实为空。前三种进入错误态并展示可定位原因，只有第四种可提示“未找到符合全部约束的食谱”。
4. `onError` 回调中的 `throw` 不能代替 Promise reject。底层流读取错误必须 reject 到 `requestRecipes`，再由页面 `catch` 处理；不得捕获后静默跳过整个响应，也不得把异常转换为空数组。
5. SSE 帧解析应兼容上游实际增量字段，并在开发验收中确认至少收到一个非空内容片段；未知帧可以忽略，但若直到流结束都没有内容，必须报告“模型未返回可解析内容”，不能伪装成业务无推荐。
6. 验收至少覆盖：正常流被完整拼接并得到候选；JSON 跨多个 chunk 时仍能解析；上游 4xx/5xx；流中途断开；无效 JSON；全部候选命中过敏原。每种情况都应结束 loading、保留用户输入并提供重试，且错误文案与真实类别一致。

## 发布路由与认证约束（强制）

### 路由
- 秒哒静态发布默认使用 `HashRouter`，页面地址形如 `/#/meals`。不要使用 `BrowserRouter` 配合 `<Navigate to="/meals">`，除非已用发布服务器验证任意深层路径都回退到 `index.html`。
- 生产验收至少检查：首次访问 `/`、应用内进入每个页面、在每个目标页面刷新、复制地址重新打开。网络响应必须返回应用 HTML，`#root` 必须有内容。
- 路由错误和运行错误必须由可见 Error Boundary 展示错误与“返回首页/重试”操作，不能只在控制台记录。

### 数据与认证
- 默认免登录模式不得创建 Supabase 表、RLS 或匿名认证依赖；使用本地持久化即可，存储键统一以 `${VITE_APP_ID}:nutrition:` 开头，避免不同应用互相覆盖。
- 仅当用户明确要求账户或跨设备数据时才接入 Supabase。接入前检查平台是否启用目标认证方式；不得假设 `signInAnonymously()` 可用。
- 若选择匿名认证，必须先验证匿名登录实际成功再建立依赖 `auth.uid()` 的数据；收到 4xx/422 时立即结束 loading、显示“当前环境未启用匿名登录”，并提供重试或真实登录路径。
- Auth 初始化必须使用 `try/catch/finally`，无论网络、CORS、认证或查询失败都要在 `finally` 结束 loading。页面不能因认证初始化失败保持空白或永久骨架屏。
- RLS 表只用于真实 authenticated 用户；禁止一边依赖 `authenticated` 策略，一边在匿名登录失败后继续执行数据库写入。

### 最小发布验收
1. 生产构建通过。
2. `/` 首屏可见且不是空 `#root`。
3. `/#/meals`、`/#/profile` 等路由刷新后仍可见。
4. 默认免登录完成“建档 → 生成食谱 → 保存 → 刷新恢复”。
5. 若启用账户，真实完成登录后再验证同一闭环；登录失败有可见错误和重试。
6. 浏览器控制台无未处理异常，Network 无页面路由 404。
